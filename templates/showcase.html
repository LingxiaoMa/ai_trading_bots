Bot design and parameterisation

A practical discussion of configuration choices, hypothesis space, dimensionality, evaluation cost and the resulting parameterisation.

Configuration and hypothesis space

The representation language is a continuous 14-dimensional parameter vector. Each candidate solution encodes a complete trading strategy by defining the parameters for two parallel composite lines — FAST and SLOW — each built from three weighted moving-average components (SMA, LMA, EMA) plus a smoothing alpha. Fast/Slow component separation reduces degenerate solutions and keeps the hypothesis space tractable for metaheuristic search.

3Fast EMA WeightWeight assigned to the EMA component of the fast signal

5Fast LMA WindowWindow size used for the fast LMA filter

12Slow LMA WindowWindow size used for the slow LMA filter

14Slow EMA AlphaExponential decay factor used for the slow EMA

Search space constraints

The design enforces short-term FAST windows (2-40) and longer-term SLOW windows (21-100). This prevents the optimizer from selecting illogical configurations where the FAST component is slower than the SLOW component. It also acts as a regularizer, reducing overfitting risk while preserving enough flexibility to capture market structure.

Resulting parameterisation

  • FAST and SLOW each combine SMA/LMA/EMA weights and duration controls.
  • EMA alpha is tuned alongside moving-average durations for adaptive smoothing.
  • Final hypotheses balance responsiveness with trend stability.
  • The 14-dimensional parameter set is well suited for CS, ALO, SA and PSO search strategies.

Iteration and learning

  • Initial trials with fully unconstrained ranges produced inconsistent FAST/SLOW behaviour.
  • Introducing asymmetric window bounds improved signal stability and reduced noisy crossovers.
  • Empirical evaluation showed that narrower hypothesis spaces led to better out-of-sample resilience.
  • Practicality dictated a compact yet rich parameterisation that the metaheuristics could explore efficiently.

Evaluation framework

The evaluation function drives the entire optimisation loop. Given a candidate 14-dimensional parameter vector, it constructs the FAST and SLOW composite lines, detects crossover signals, and simulates a full portfolio backtest with a 3% transaction fee to produce a single fitness score.

The pseudocode below formalises this process. Each metaheuristic algorithm calls this function thousands of times, treating the returned cash value as the objective to maximise.

Algorithm 1  Trading Bot Evaluation Framework

 1:  parameters    ← CandidateSolution
 2:  price_series  ← Historical Bitcoin prices
 3:  fast_params   ← parameters[0:7]
 4:  slow_params   ← parameters[7:14]
 5:  fast_line     ← BuildCompositeLine(price_series, fast_params)
 6:  slow_line     ← BuildCompositeLine(price_series, slow_params)
 7:  signals       ← ∅
 8:  for each time step t in price_series do
 9:      if fast_line crosses above slow_line then
10:          signals[t] ← BUY
11:      else if fast_line crosses below slow_line then
12:          signals[t] ← SELL
13:      else
14:          signals[t] ← HOLD
15:      end if
16:  end for
17:  cash    ← InitialCash
18:  bitcoin ← 0
19:  for each time step t in price_series do
20:      if signals[t] = BUY and cash > 0 then
21:          bitcoin ← cash converted to Bitcoin after fee
22:          cash    ← 0
23:      else if signals[t] = SELL and bitcoin > 0 then
24:          cash    ← bitcoin converted to cash after fee
25:          bitcoin ← 0
26:      end if
27:  end for
28:  if bitcoin > 0 then
29:      cash ← bitcoin converted to cash at final price after fee
30:  end if
31:  fitness ← cash
32:  return fitness

Simulated Annealing

thermostat

Metallurgical cooling inspiration. Temperature-modulated probabilistic acceptance of worse solutions enables shallow local optimum escape.

Algorithm 3  Simulated Annealing (SA)

 1: CurrentSolution ← RandomCandidate()
 2: CurrentFitness ← EvaluateFitness(CurrentSolution)
 3: BestSolution ← CurrentSolution
 4: BestFitness ← CurrentFitness
 5: Temperature ← InitialTemperature
 6: repeat
 7:     NeighbourSolution ← Perturb(CurrentSolution)
 8:     NeighbourSolution ← ApplyBounds(NeighbourSolution)
 9:     NeighbourFitness ← EvaluateFitness(NeighbourSolution)
10:     if NeighbourFitness > CurrentFitness then
11:         CurrentSolution ← NeighbourSolution
12:         CurrentFitness ← NeighbourFitness
13:         if CurrentFitness > BestFitness then
14:             BestSolution ← CurrentSolution
15:             BestFitness ← CurrentFitness
16:         end if
17:     else
18:         AcceptProb ← exp((NeighbourFitness - CurrentFitness) / Temperature)
19:         if Random(0,1) < AcceptProb then
20:             CurrentSolution ← NeighbourSolution
21:             CurrentFitness ← NeighbourFitness
22:         end if
23:     end if
24:     Temperature ← Temperature × CoolingRate
25: until maximum evaluations reached
26: return BestSolution

Cuckoo Search

Lévy Flight-based exploration with heavy-tailed random walks. Breaks local optima traps through sudden massive parameter leaps.

Algorithm 5  Cuckoo Search (CS)

 1: NestPopulation ← RandomPopulation()
 2: EvaluateFitness(NestPopulation)
 3: BestNest ← BestSolution(NestPopulation)
 4: repeat
 5:     for each nest do
 6:         NewNest ← LevyFlight(BestNest)
 7:         NewNest ← ApplyBounds(NewNest)
 8:         NewFitness ← EvaluateFitness(NewNest)
 9:         RandomNest ← RandomSelection()
10:         if NewFitness > Fitness(RandomNest) then
11:             Replace(RandomNest, NewNest)
12:         end if
13:         if NewFitness > Fitness(BestNest) then
14:             BestNest ← NewNest
15:         end if
16:     end for
17:     DiscoveryStep()
18:     ReplaceDiscoveredNests()
19: until maximum iterations reached
20: return BestNest
[03] POPULATION

Antlion Optimizer

hub

Swarm intelligence with adaptive boundary shrinking. Balances ant exploration vs. antlion exploitation through dynamic constraint coupling.

Algorithm 4  Antlion Optimizer (ALO)

 1: AntlionPopulation ← RandomPopulation()
 2: EvaluateFitness(AntlionPopulation)
 3: Elite ← BestAntlion(AntlionPopulation)
 4: repeat
 5:     for each ant do
 6:         SelectedAntlion ← RouletteWheelSelection()
 7:         Walk1 ← RandomWalk(SelectedAntlion)
 8:         Walk2 ← RandomWalk(Elite)
 9:         Ant ← Average(Walk1, Walk2)
10:         Ant ← ApplyBounds(Ant)
11:     end for
12:     EvaluateFitness(AllAnts)
13:     CombinedPopulation ← Antlions ∪ Ants
14:     KeepBestSolutions(CombinedPopulation)
15:     Elite ← BestAntlion(CombinedPopulation)
16:     ShrinkSearchBoundaries()
17: until maximum iterations reached
18: return Elite
[04] POPULATION

Particle Swarm Optimisation

scatter_plot

Population-based swarm intelligence inspired by collective social behaviour. Each particle represents a candidate trading strategy; positions update via three components — inertia, personal best experience, and global swarm knowledge.

Algorithm 6  Particle Swarm Optimisation (PSO)

 1: Initialise particle positions
 2: Initialise particle velocities
 3: EvaluateFitness(AllParticles)
 4: PersonalBest ← ParticlePositions
 5: GlobalBest ← BestParticle()
 6: repeat
 7:     for each particle do
 8:         CognitiveComponent ← distance to PersonalBest
 9:         SocialComponent ← distance to GlobalBest
10:         Velocity ← Inertia + CognitiveComponent + SocialComponent
11:         Update particle position
12:         Apply parameter bounds
13:         CurrentFitness ← EvaluateFitness(Particle)
14:         if CurrentFitness > PersonalBestFitness then
15:             Update PersonalBest
16:         end if
17:         if CurrentFitness > GlobalBestFitness then
18:             Update GlobalBest
19:         end if
20:     end for
21: until maximum evaluations reached
22: return GlobalBest

Experiments and evaluation

Detailed training and validation setup, with experiment design and evaluation criteria for the trading agent.

Training protocol

  • Training on pre-2020 Bitcoin history, limiting overfitting to the chosen regime.
  • Fixed 9,000-evaluation budget per algorithm for fair comparison.
  • Single-segment and multi-segment fitness functions probe robustness.
  • High/Low signal component constraints improve filter consistency.

Validation strategy

  • Out-of-sample testing on 2020+ BTC prices with transaction cost model.
  • Buy-and-hold benchmark used to measure live-market resilience.
  • Interactive signal charts verify trade entry and exit quality.
  • Performance metrics focused on generalization rather than training peak only.

Experiment variables

  • Algorithm type: CS, ALO, SA, PSO.
  • Signal design: 14 parameters controlling FAST/SLOW crossover filters.
  • Regime tests: single-segment vs multi-segment training objectives.
  • Evaluation focus: portfolio growth, convergence stability, and signal interpretability.

Experiment Overview

Four experiments were conducted to comprehensively evaluate optimization algorithms across different data frequencies, out-of-sample generalization, and market regime robustness.

  • Experiment 1: Daily training convergence—comparative analysis of RS, SA, ALO, CS, and PSO on pre-2020 Bitcoin daily data (9,000 evaluations per algorithm).
  • Experiment 2: Hourly training complexity—evaluation of computational cost and landscape complexity when using hourly data (30–50x more observations than daily).
  • Experiment 3: Out-of-sample generalization—testing optimized strategies on 2020+ Bitcoin data to measure true robustness and regime adaptability.
  • Experiment 4: Multi-segment robustness—optimization across four distinct market regimes (2014–2016 sideways, 2017 bull, 2018 bear, 2019 recovery) to discover generalizable parameters.

Experiment 2: Convergence on Hourly Training Data

Evaluation on hourly Bitcoin data reveals substantially higher computational complexity. Algorithms require significantly more evaluations for convergence due to increased trading signal frequency and market volatility.

Resolution Comparison Summary

Hourly data generates 30-50x more observations than daily data, resulting in:

  • Exponentially higher computational requirements
  • Longer convergence times across all algorithms
  • Increased optimization landscape complexity
  • Minute-level data deemed computationally infeasible

Decision: All subsequent experiments use daily data to maintain computational feasibility while preserving statistical rigor.

Discussion and Conclusions

Four key findings from the comparative experiments, covering benchmark dependency, bias-variance trade-offs, population diversity, and global exploration.

[01]

Buy & Hold Benchmark and Regime Dependency

The superior performance of Buy & Hold ($6,016) was determined by the test dataset's characteristics rather than inherent strategy superiority. During the 2020–2022 testing period, Bitcoin rose from $7,200 to $43,000. In such regimes, holding is optimal — active algorithms risk missing upward movements and incur 3% transaction fees per trade.

However, B&H is not robust. During the 2018 bear market, B&H suffered an 82% loss, whereas trend-following algorithms would significantly outperform it. B&H's success in this experiment reflects coincidental timing rather than true adaptability to varying market environments.

[02]

Limited Exploration: SA in Single-Segment

SA achieved $4,207 out-of-sample, outperforming CS ($3,377), PSO ($2,722), and ALO ($2,234). SA's rapid cooling rate (0.98) caused it to converge early to a "good enough" local optimum, preventing it from over-fitting the training data's noise.

Conversely, population-based algorithms performed aggressive exploitation, leading to severe overfitting. PSO achieved the highest training fitness ($46,705) but yielded only $2,722 in testing. This illustrates the bias-variance trade-off: SA's limited exploration resulted in higher bias but lower variance, yielding superior generalisation.

[03]

Population Diversity in Multi-Segment Environments

The multi-segment fitness function required stable average performance across four distinct market regimes. Under these conditions, SA's single-state nature became a liability — once trapped in a new local optimum, it lacked mechanisms to maintain alternative candidates, causing its test performance to drop to $3,381.

Population-based algorithms possessed a structural advantage by continuously maintaining 30 candidate solutions across different regions of the parameter space. This increased the probability of discovering parameters that generalised well across all historical phases, allowing ALO, PSO, and CS to all surpass SA in out-of-sample performance.

[04]

Global Exploration: CS vs. ALO and PSO

CS demonstrated superior robustness in the multi-segment framework, achieving the highest out-of-sample performance ($5,495), surpassing ALO ($4,971) and PSO ($4,712). ALO's roulette-wheel selection and boundary contraction, and PSO's velocity inertia, are highly efficient exploiters — but if populations converge into a regime-specific local optimum, they lack mechanisms to escape.

CS uses Lévy Flights with heavy-tailed step sizes that produce occasional extremely large jumps. Combined with periodic nest replacement (pa=0.25), CS maintains high population diversity and discovered genuinely robust parameters across all market regimes.
